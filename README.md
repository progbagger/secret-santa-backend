# secret-santa-backend

Backend для сервиса «Тайный Санта». Он хранит пользователей, игры и результаты жеребьёвок, выполняет бизнес-сценарии и предоставляет версионированный HTTP API.

## Ответственность backend

Backend должен:

- идемпотентно регистрировать пользователей по уникальному логину и хранить изменяемые данные профиля отдельно от идентичности;
- управлять играми, участниками, правилами и сроками;
- явно проверять допустимость переходов состояния игры;
- перед жеребьёвкой проверять существование полного допустимого назначения;
- атомарно сохранять результаты жеребьёвки в PostgreSQL;
- возвращать клиенту только те данные, которые нужны для конкретного публичного или приватного сценария;
- предоставлять стабильный версионированный HTTP-контракт и OpenAPI-схему.

Логин — непрозрачная для backend строка: клиент сам определяет её источник и формат. Доступ к HTTP API требует сервисной аутентификации. Пользовательская аутентификация — отдельная задача.

## Архитектура и технологии

Целевой стек backend:

- Python 3.14 и полностью асинхронный I/O;
- FastAPI для HTTP API;
- PostgreSQL, SQLAlchemy asyncio и asyncpg для долговременного состояния;
- Alembic для последовательных миграций схемы;
- Redis только для короткоживущих блокировок, дедупликации или координации, если конкретный сценарий этого потребует;
- `uv` для зависимостей и запуска команд;
- Ruff, mypy, pytest и pre-commit для локальных проверок и CI.

Код добавляется по мере появления функциональности, без пустых архитектурных слоёв. Целевая структура:

- `src/secret_santa_backend/web/` — FastAPI app и маршруты;
- `src/secret_santa_backend/web/entities/` — модели HTTP-запросов и ответов;
- `src/secret_santa_backend/services/` — бизнес-правила, orchestration и границы транзакций;
- `src/secret_santa_backend/repositories/postgres/` — атомарные операции с PostgreSQL и преобразование строк во внутренние модели;
- `src/secret_santa_backend/entities/` — внутренние модели и value objects;
- `alembic/` — миграции PostgreSQL;
- `tests/functional/` — проверка запущенного приложения и реальной PostgreSQL через внешние протоколы;
- `tests/units/` — простая детерминированная логика без тяжёлых моков.

Репозитории не делают скрытых `commit` или `rollback`. Сервисный слой задаёт транзакцию вокруг полного изменения бизнес-состояния. PostgreSQL остаётся источником истины для пользователей, игр, участников, правил и результатов жеребьёвки.

Lifespan приложения создаёт единственный экземпляр БД и закрывает его при завершении. Общая async-зависимость FastAPI привязывает БД к контексту запроса; сервисы используют `transaction()` из PostgreSQL-репозитория без передачи соединения через аргументы. Контекст сбрасывается после запроса, в том числе при ошибке или отмене.

## HTTP API

HTTP-контракт backend размещается под префиксом `/api/v1`. HTTP-модели не выдают наружу SQLAlchemy entities, а операции получают стабильные `operationId` в OpenAPI.

### Сервисная аутентификация

Все маршруты `/api/v1` требуют заголовок `Authorization: Bearer <access_token>`. Токен подтверждает доступ клиентского сервиса. Клиент определяет, какой пользователь запросил действие. Бэкенд проверяет принадлежность ресурсов указанному организатору.

Отдельный сервис `token-issuer` выдаёт короткоживущие токены:

1. Клиент отправляет `POST /token` с HTTP Basic (пользователь `bot`, пароль из `TOKEN_BOT_CLIENT_SECRET`) и телом `grant_type=client_credentials` в формате `application/x-www-form-urlencoded`.
2. Успешный ответ содержит `access_token`, `token_type: Bearer` и `expires_in` в секундах. Сохраните токен в памяти клиента и передавайте его только в заголовке `Authorization` запросов к бэкенду. В Swagger UI можно ввести токен через **Authorize**.
3. До истечения срока клиент повторяет запрос на `/token` с теми же реквизитами. При одновременных запросах используйте одно обновление на процесс клиента. Старый токен действует до своего срока, поэтому запросы с ним могут завершиться во время обновления.
4. Если бэкенд вернул `401` с `WWW-Authenticate: Bearer`, получите новый токен и повторите исходный запрос один раз. Middleware отклоняет такой запрос до вызова обработчика. При `503` сервис проверки недоступен. Запрос также завершается до обработчика.

Бэкенд проверяет токены через `POST /introspect` с отдельными реквизитами `backend` и `TOKEN_BACKEND_CLIENT_SECRET`. Сервис выдачи хранит хеши токенов в памяти одного процесса. После его перезапуска прежние токены отклоняются, а клиент может запросить новый. Держите сервисные секреты в конфигурации развёртывания. При передаче между хостами используйте HTTPS с проверкой сертификата.

### Регистрация пользователя

`POST /api/v1/users` принимает уникальный непустой логин длиной до 255 символов:

```json
{
  "login": "123456789"
}
```

При первой регистрации backend возвращает `201 Created`. Повторный или конкурентный запрос с тем же логином возвращает `200 OK` и того же пользователя, поэтому retry не создаёт дубликат. Некорректное тело запроса возвращает `422 Unprocessable Entity`.

Пример ответа:

```json
{
  "id": 1,
  "login": "123456789",
  "created_at": "2026-10-15T12:00:00Z",
  "updated_at": "2026-10-15T12:00:00Z"
}
```

PostgreSQL назначает целочисленный `id`. Поле `login` участвует в уникальности без знания о внешней платформе.

### Игры организатора

Организатор может создать несколько игр с любыми названиями и независимыми составами. Его внутренний ID передаётся в пути как `organizer_user_id`.

| Метод | Путь | Успешный ответ | operationId |
| --- | --- | --- | --- |
| POST | `/api/v1/users/{organizer_user_id}/games` | `201 Created` | `create_game` |
| GET | `/api/v1/users/{organizer_user_id}/games` | `200 OK` | `list_games` |
| GET | `/api/v1/users/{organizer_user_id}/games/{game_id}` | `200 OK` | `get_game` |
| PATCH | `/api/v1/users/{organizer_user_id}/games/{game_id}` | `200 OK` | `update_game` |
| DELETE | `/api/v1/users/{organizer_user_id}/games/{game_id}` | `204 No Content` | `delete_game` |
| GET | `/api/v1/users/{organizer_user_id}/games/{game_id}/participants` | `200 OK` | `list_game_participants` |
| PUT | `/api/v1/users/{organizer_user_id}/games/{game_id}/participants/{user_id}` | `204 No Content` | `add_game_participant` |
| DELETE | `/api/v1/users/{organizer_user_id}/games/{game_id}/participants/{user_id}` | `204 No Content` | `remove_game_participant` |

Пример тела запроса на создание игры.

```json
{
  "name": "Новый год 2026",
  "description": "Семья и друзья",
  "starts_at": "2026-12-20T12:00:00+07:00",
  "ends_at": "2026-12-31T18:00:00+07:00"
}
```

Игра содержит `id` в формате UUID, `organizer_user_id`, `name`, `description`, `starts_at`, `ends_at`, `created_at` и `updated_at`. GET коллекции возвращает только игры указанного организатора, отсортированные по дате создания и UUID. У зарегистрированного организатора без игр список пуст.

Имя обрезается по краям и должно содержать от 1 до 120 символов после нормализации. Описание необязательно. Оно допускает `null` и строки длиной до 2000 символов, включая пустую. Пробелы в описании сохраняются.

Каждый срок можно указать строкой даты и времени с часовым поясом, передать как `null` или опустить. API возвращает заданные сроки в UTC. Если заданы оба, `ends_at` должен быть позже `starts_at`. Сроки задают расписание игры. Запуск игры и закрытие регистрации относятся к отдельным сценариям.

PATCH принимает только `name`, `description`, `starts_at` и `ends_at`. Пропущенные поля сохраняют прежние значения. `null` очищает описание или соответствующий срок. Пустое тело, неизвестные поля, `name: null` и невалидные значения дают `422`. При частичном обновлении проверяется итоговая пара сроков. Если она недопустима, все поля сохраняют прежние значения. Повтор тех же значений сохраняет `updated_at`.

Неизвестный организатор, чужая и отсутствующая игра возвращают одинаковый `404` с `{"detail":"Game or organizer not found"}`. Это относится и к операциям с составом. DELETE игры удаляет её состав. Участники остаются зарегистрированными пользователями, а составы других игр сохраняются.

GET состава возвращает объекты вида `{"user_id": 1}` по возрастанию внутреннего ID. PUT включает зарегистрированного пользователя в состав по его внутреннему `user_id`. Организатор может добавить себя. Добавление неизвестного пользователя возвращает `404` с `{"detail":"User not found"}`. Повторный PUT оставляет одну запись. DELETE участника возвращает `204`, в том числе если пользователь уже отсутствует в составе.

Миграция `0003` переименовывает таблицу `santa_groups` в `santa_games`. UUID, владельцы, названия, описания, timestamps и зарегистрированные пользователи сохраняются. У перенесённых игр сроки равны `null`, а составы пусты. Клиенты переходят с `/groups` на `/games` и продолжают обращаться к перенесённым записям по тем же UUID. Миграцию применяет `alembic upgrade head` при запуске Compose или при ручном обновлении. При откате до `0002` восстанавливается прежняя схема групп, а сохранённые сроки и составы удаляются.

### Служебные endpoints

- `GET /health/live` — процесс backend запущен;
- `GET /health/ready` — PostgreSQL и сервис выдачи токенов доступны;
- `/docs` — Swagger UI;
- `/redoc` — ReDoc;
- `/openapi.json` — OpenAPI-схема.

Эти служебные маршруты доступны без Bearer-токена.

Пользовательские и игровые данные требуют минимального раскрытия. Имена, username и другие изменяемые поля не используются как идентичность или средство авторизации. Пары жеребьёвки, пожелания и приватные сообщения не попадают в общие ответы и диагностические логи.

## Тестирование

Основной уровень проверки бизнес-сценариев — функциональные тесты на pytest. Они запускают настоящее приложение отдельным процессом, поднимают PostgreSQL и при необходимости Redis через Docker Compose на свободных портах, взаимодействуют с backend по HTTP и проверяют сохранённое состояние через SQL.

Функциональные тесты не импортируют бизнес-код из `src`, не подменяют handlers, services или repositories и не используют произвольные `sleep`. Готовность приложения и фоновую работу следует ждать по наблюдаемому состоянию с ограниченным polling. Unit-тесты применяются для чистой валидации, форматирования, переходов состояний и алгоритма жеребьёвки.

## Локальная разработка

Для запуска нужны Docker с Compose и свободные порты `8000`, `8001` и `5432`. Сгенерируйте два разных секрета и экспортируйте их в окружение или сохраните в локальном `.env`:

```bash
export TOKEN_BOT_CLIENT_SECRET="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
export TOKEN_BACKEND_CLIENT_SECRET="$(python3 -c 'import secrets; print(secrets.token_urlsafe(32))')"
docker compose up --build
```

Compose поднимает PostgreSQL и `token-issuer`, применяет `alembic upgrade head` и запускает бэкенд на <http://127.0.0.1:8000>. Сервис выдачи доступен с хоста на <http://127.0.0.1:8001> и по адресу `http://token-issuer:8000` внутри сети Compose. Порты хоста можно изменить через `BACKEND_PORT`, `TOKEN_ISSUER_PORT` и `POSTGRES_PORT`:

```bash
BACKEND_PORT=8080 TOKEN_ISSUER_PORT=8081 POSTGRES_PORT=5433 docker compose up --build
```

Остановить окружение:

```bash
docker compose down
```

Чтобы вместе с контейнерами удалить локальные данные PostgreSQL, добавьте флаг `--volumes`.

Значения `secret_santa` в `compose.yml` предназначены только для локальной разработки. При развёртывании задайте собственные `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD`.

Для запуска backend напрямую сначала установите зависимости:

```bash
uv sync --locked --all-groups
```

Затем запустите PostgreSQL и сервис выдачи с двумя экспортированными секретами:

```bash
uv run uvicorn secret_santa_backend.token_issuer:create_app --factory --host 127.0.0.1 --port 8001
```

В другом терминале примените миграции и запустите бэкенд с тем же `TOKEN_BACKEND_CLIENT_SECRET`:

```bash
export DATABASE_URL='postgresql+asyncpg://secret_santa:secret_santa@127.0.0.1:5432/secret_santa'
export TOKEN_ISSUER_URL='http://127.0.0.1:8001'
uv run alembic upgrade head
uv run secret-santa-backend
```

Бэкенду нужны `DATABASE_URL`, `TOKEN_ISSUER_URL` (origin сервиса выдачи) и `TOKEN_BACKEND_CLIENT_SECRET`. В Compose для URL по умолчанию используется адрес контейнера. При переносе сервиса задайте новый HTTPS-origin в конфигурации бэкенда и клиента. Оба секрета должны быть разными URL-safe строками длиной от 32 символов. `TOKEN_TTL_SECONDS` настраивает срок токена у сервиса выдачи. По умолчанию 900 секунд, допустимый диапазон от 1 до 3600.

Адрес и порт приложения настраиваются переменными `BACKEND_HOST` и `BACKEND_PORT`; значения по умолчанию — `0.0.0.0` и `8000`.

Установить Git hooks:

```bash
uv run pre-commit install --hook-type pre-commit --hook-type post-merge
```

Запустить проверки:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy .
uv run pytest tests/units -q
uv run pytest tests/functional -q
```

Функциональным тестам нужен работающий Docker. Они сами запускают PostgreSQL, бэкенд и сервис выдачи токенов на свободных локальных портах и очищают окружение после выполнения.
