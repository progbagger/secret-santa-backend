# secret-santa-backend

Backend для сервиса «Тайный Санта». Он хранит пользователей, группы, игры и результаты жеребьёвок, выполняет бизнес-сценарии и предоставляет версионированный HTTP API.

## Ответственность backend

Backend должен:

- идемпотентно регистрировать пользователей по уникальному логину и хранить изменяемые данные профиля отдельно от идентичности;
- управлять группами, играми, участниками, правилами и сроками;
- явно проверять допустимость переходов состояния игры;
- перед жеребьёвкой проверять существование полного допустимого назначения;
- атомарно сохранять результаты жеребьёвки в PostgreSQL;
- возвращать клиенту только те данные, которые нужны для конкретного публичного или приватного сценария;
- предоставлять стабильный версионированный HTTP-контракт и OpenAPI-схему.

Логин — непрозрачная для backend строка: клиент сам определяет её источник и формат. Пароль и сервисная аутентификация будут добавлены отдельной задачей.

## Архитектура и технологии

Целевой стек backend:

- Python 3.14 и полностью асинхронный I/O;
- FastAPI для HTTP API;
- PostgreSQL, SQLAlchemy asyncio и asyncpg для долговременного состояния;
- Alembic для последовательных миграций схемы;
- Redis только для короткоживущих блокировок, дедупликации или координации, если конкретный сценарий этого потребует;
- `uv` для зависимостей и запуска команд;
- Ruff, mypy, pytest и pre-commit для локальных проверок и CI.

Код добавляется по мере появления функциональности, без пустых архитектурных слоёв. Целевая структура:

- `src/secret_santa_backend/web/` — FastAPI app и маршруты;
- `src/secret_santa_backend/web/entities/` — модели HTTP-запросов и ответов;
- `src/secret_santa_backend/services/` — бизнес-правила, orchestration и границы транзакций;
- `src/secret_santa_backend/repositories/postgres/` — атомарные операции с PostgreSQL и преобразование строк во внутренние модели;
- `src/secret_santa_backend/entities/` — внутренние модели и value objects;
- `alembic/` — миграции PostgreSQL;
- `tests/functional/` — проверка запущенного приложения и реальной PostgreSQL через внешние протоколы;
- `tests/units/` — простая детерминированная логика без тяжёлых моков.

Репозитории не делают скрытых `commit` или `rollback`. Сервисный слой задаёт транзакцию вокруг полного изменения бизнес-состояния. PostgreSQL остаётся источником истины для пользователей, групп, игр, участников, правил и результатов жеребьёвки.

## HTTP API

HTTP-контракт backend размещается под префиксом `/api/v1`. HTTP-модели не выдают наружу SQLAlchemy entities, а операции получают стабильные `operationId` в OpenAPI.

### Регистрация пользователя

`POST /api/v1/users` принимает уникальный непустой логин длиной до 255 символов:

```json
{
  "login": "123456789"
}
```

При первой регистрации backend возвращает `201 Created`. Повторный или конкурентный запрос с тем же логином возвращает `200 OK` и того же пользователя, поэтому retry не создаёт дубликат. Некорректное тело запроса возвращает `422 Unprocessable Entity`.

Пример ответа:

```json
{
  "id": 1,
  "login": "123456789",
  "created_at": "2026-10-15T12:00:00Z",
  "updated_at": "2026-10-15T12:00:00Z"
}
```

PostgreSQL назначает целочисленный `id`. Поле `login` участвует в уникальности без знания о внешней платформе.

### Служебные endpoints

- `GET /health/live` — процесс backend запущен;
- `GET /health/ready` — backend готов принимать запросы и PostgreSQL доступна;
- `/docs` — Swagger UI;
- `/redoc` — ReDoc;
- `/openapi.json` — OpenAPI-схема.

До появления отдельного сценария сервисной аутентификации API считается внутренним: его вызывает доверенный клиент, и его не следует публиковать напрямую в интернет.

Пользовательские и игровые данные требуют минимального раскрытия. Имена, username и другие изменяемые поля не используются как идентичность или средство авторизации. Пары жеребьёвки, пожелания и приватные сообщения не попадают в общие ответы и диагностические логи.

## Тестирование

Основной уровень проверки бизнес-сценариев — функциональные тесты на pytest. Они запускают настоящее приложение отдельным процессом, поднимают PostgreSQL и при необходимости Redis через Docker Compose на свободных портах, взаимодействуют с backend по HTTP и проверяют сохранённое состояние через SQL.

Функциональные тесты не импортируют бизнес-код из `src`, не подменяют handlers, services или repositories и не используют произвольные `sleep`. Готовность приложения и фоновую работу следует ждать по наблюдаемому состоянию с ограниченным polling. Unit-тесты применяются для чистой валидации, форматирования, переходов состояний и алгоритма жеребьёвки.

## Локальная разработка

Для запуска всего окружения нужны Docker с Compose и свободные порты `8000` и `5432`:

```bash
docker compose up --build
```

Compose поднимает PostgreSQL, применяет `alembic upgrade head` и запускает backend на <http://127.0.0.1:8000>. Порты хоста можно изменить через `BACKEND_PORT` и `POSTGRES_PORT`:

```bash
BACKEND_PORT=8080 POSTGRES_PORT=5433 docker compose up --build
```

Остановить окружение:

```bash
docker compose down
```

Чтобы вместе с контейнерами удалить локальные данные PostgreSQL, добавьте флаг `--volumes`.

Значения `secret_santa` в `compose.yml` предназначены только для локальной разработки. При развёртывании задайте собственные `POSTGRES_DB`, `POSTGRES_USER` и `POSTGRES_PASSWORD`.

Для запуска backend напрямую сначала установите зависимости:

```bash
uv sync --locked --all-groups
```

Затем запустите PostgreSQL, примените миграции и стартуйте приложение:

```bash
export DATABASE_URL='postgresql+asyncpg://secret_santa:secret_santa@127.0.0.1:5432/secret_santa'
uv run alembic upgrade head
uv run secret-santa-backend
```

`DATABASE_URL` обязателен. Адрес и порт приложения настраиваются переменными `BACKEND_HOST` и `BACKEND_PORT`; значения по умолчанию — `0.0.0.0` и `8000`.

Установить Git hooks:

```bash
uv run pre-commit install --hook-type pre-commit --hook-type post-merge
```

Запустить проверки:

```bash
uv run ruff check .
uv run ruff format --check .
uv run mypy .
uv run pytest tests/units -q
uv run pytest tests/functional -q
```

Функциональным тестам нужен работающий Docker. Они сами запускают PostgreSQL и backend на свободных локальных портах и очищают окружение после выполнения.
